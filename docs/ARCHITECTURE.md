# 架构与设计约束

## 处理模型

Job Mail Assistant 是单进程、顺序执行的处理流程：

```text
QQ IMAP → 候选邮件过滤 → AI 结构化提取 → 确定性时间解析
        → 飞书 Base 持久化 → iCloud CalDAV → QQ SMTP 报告
```

除非明确进行架构变更，否则不得引入数据库、Web 服务、Agent framework 或并行写入者。
飞书 Base 同时保存业务记录和唯一的持久化运行游标。

## 邮件扫描与身份识别

默认 `SCAN_DAYS=2` 是每次运行的最小扫描窗口，不是状态游标。程序会读取飞书中上次成功运行时间：若距今超过 2 天，就按经过的天数自动扩大回扫范围，以补足漏跑期间的邮件。对完整、明确、可执行的重复邮件，应在 AI 解析前跳过：
优先使用规范化的 `Message-ID`，缺失时使用确定性的 fallback fingerprint。

候选过滤除测评、笔试、面试和招聘进展外，也接受同时包含招聘语境、投递/申请动作与明确
截止表达的岗位邮件。普通岗位推广仍应排除。Multipart 邮件在纯文本与 HTML 渲染文本之间
选择信息更完整的一份，避免纯文本占位隐藏 HTML 中的职位和截止日期。候选规则变更不主动
回扫早于正常窗口的历史邮件。

只有当已持久化记录的确认说明明确指出可确定修复的 parser 缺陷时，完全相同的邮件才可
重新处理。目前允许修复的缺陷仅包括：缺失明确日期组成部分，或唯一 action URL 被拒绝。
测评、笔试和异步 AI 面试邀请若同时包含生效和失效时刻，只能把唯一且明确标注“失效”
的完整时刻作为截止时间；解析器在 AI 漏提取或误取生效时间时可据此纠正。扫描窗口内，
这类邮件若已持久化时间缺失或与该失效时刻不符，也允许重处理。修复完成后，该邮件
重新进入正常的重复跳过路径。

正文明确给出接收邮件后起算的相对截止时间或唯一链接有效期时，确定性解析器核对数值与
单位，不采用 AI 误提取的单位或自行生成的绝对日期。冲突时长进入人工确认；正文存在明确
日期或点击/登录后起算表达时，不使用这条自动修复规则。已有 deadline 测评、笔试、AI
面试记录时间不符且邮件接收时间仍与源邮件相同，可修复并重新进入去重路径；较旧的线程
邮件不得覆盖较新的记录。定向修复命令只更新指定公司的匹配记录与相同 UID 日历，不调用
AI、不发送报告、不推进游标，dry-run 不产生写入。

线程更新只能使用 `References` 或 `In-Reply-To` 的精确匹配。非线程合并要求公司、岗位、
事项类型和解析后的时间全部精确相同，不得引入模糊语义合并。

IMAP 必须保持只读，并以服务器 `INTERNALDATE` 作为权威接收时间。不得依赖已读/未读状态
或邮件头中的 `Date`。

## AI 与时间解析

AI 输出是不可信的结构化提取结果，必须使用 Pydantic 验证。不得把 AI 生成的最终 datetime
作为权威值。小时、自然日、中国工作日、明确日期、星期表达、跨年保护和仅用于展示的默认
时长均由 Python 确定性解析。所有时间统一为 `Asia/Shanghai`。

Structured Output 和 JSON Object 两种请求模式都提供完整 JSON Schema。JSON 解码或
Pydantic 校验失败时，用不包含原始输出的字段/错误类型反馈重新提取，最多尝试 3 次；
不得用宽松解析绕过校验。最终失败不写入该邮件事项、不推进成功游标。应用诊断日志只
记录安全的错误分类，隐藏 HTTP 请求 URL 中的私人资源标识。

思考模式由可选配置 `AI_ENABLE_THINKING` 控制：只接受 `true`、`false` 或留空。
留空时不向服务商传递扩展参数；显式配置时，两种输出模式及重试均使用相同设置。
该开关仅用于支持 `enable_thinking` 的接口；不改变严格校验或确定性日期计算。

模糊表达、“尽快”和不受支持年份的节假日必须进入人工确认。缺少具体发生时刻的真人面试
邮件不属于已确认安排，不得创建事项。
岗位是可选信息；未提供或无法确定岗位时保持为空，不得仅因此进入人工确认，也不得在报告中显示“岗位待确认”。
工作日从邮件接收后的次日开始计算，并保留邮件接收时刻。只有日期的 deadline 解析为
23:59，同时标记为推算时间。
有明确申请入口和截止时间的岗位邮件使用事项类型“投递”；只有岗位推广、没有截止时间的
推荐邮件仍分类为 irrelevant。

真人视频、电话和现场面试只有在邮件明确确认实际面试日期和时间时才属于可持久化事项。
预约或选择面试时间、改约协商、仅有预约截止时间、面试问卷、满意度和体验反馈不得创建
Base 事项或 Calendar 事件。异步 AI 面试、测评和笔试仍可按完成截止时间持久化。

## 飞书与 Calendar 不变量

运行时代码只验证飞书 schema，不得创建、删除或修改表和字段。生产权限不包含删除或
schema 修改能力。

QQ 网页版读信链接依赖会话 `sid` 和内部 `mailid`，不能由 IMAP `UID` 或
`Message-ID` 稳定生成。系统不写入邮箱首页来冒充单封邮件链接；来源由邮件主题、
接收时间和 `Message-ID` 共同定位。

Calendar discovery 要求 `ICLOUD_CALENDAR_NAME` 恰好匹配一个日历；不得自动创建日历，
也不得在多个同名日历之间猜测。每个 Calendar UID 和资源名称由飞书 `record_id` 派生；
事项改期时必须更新同一个 UID。仅 Calendar 写入失败时，应持久化补偿状态，并且可以允许
邮件游标继续推进。淘汰或流程结束邮件不得自动删除事件或把任务标记为完成。

Calendar 事件统一使用 `Asia/Shanghai`、提前 24 小时的 DISPLAY alarm，以及确定性的展示
时长：没有结束时间的固定事项为 60 分钟，deadline 为 15 分钟。备注必须明确说明仅用于
展示的结束时间并非来自邮件原文。

## 失败与安全边界

只有在 IMAP、AI、飞书持久化和 SMTP 报告全部成功后，才推进完整成功游标。身份验证、
schema、歧义和数据验证错误都按保守失败处理；rate limit 和临时 5xx 响应使用有界指数退避
重试。

不得记录或提交邮件正文、凭据、Token、私人 Wiki/Base URL 或真实邮件 fixture。GitHub
Actions 权限保持 `contents: read`，checkout 禁止持久化凭据，Action 必须固定到不可变
commit SHA，运行配置只保存在本地 `.env` 或 Actions Secrets。
